# Files

- [Directory Registration and Discovery Workflow](directory-registration.md) - End-to-end journey of an agent appearing in and staying inside the HAAP federated directory: building and signing the key-free public manifest, POST /register submit, the registry-issued signed challenge nonce, the signed endpoint proof at POST /register/complete, 24 h entry expiry with 6 h heartbeat renewal, capability and text search, and why a discovery client must re-verify the agent's /.well-known/haap.json directly afterwards.
- [Alliance Friendship Handshake and Approval Workflow](friendship-handshake.md) - End-to-end journey of two HAAP agents becoming friends: the outbound start_friendship sequence on the client side (hello with embedded public key, hello_ack challenge, signed challenge proof, verify, friend_request), the server's self-contained fingerprint-key bootstrap verification, the directory lifecycle (pending_out / pending_in / accepted / blocked), the RequestPolicy outcomes deny / auto-approve capped by max_role / queue with the actionable human approval card, and friend_accept carrying the real granted matrix and role back to the requester.
- [Marketplace Booking Workflow (Open Services)](marketplace-booking.md) - The no-friendship-required trust mode of HAAP: how a business publishes a marketplace_catalog with an auto_accept policy and a booking on_task backend, how clients discover availability and book through the service_search / service_quote / service_book / service_cancel bootstrap messages, the shared sender checks (identity-verified, not blocked, dedicated marketplace rate limits, auto_accept gate), and how bookings reuse the task pipeline into the business backend — with demo_marketplace.py as the canonical runnable example.
- [Task Delegation Workflow and A2A Task Lifecycle](task-delegation.md) - How a friend agent delegates executable work to another accepted friend in HAAP: the outbound delegate_task pipeline with the local permission guard and outbound rate limit, the receiving server's ordered authorization gate (accepted friendship, then action+scope permission, then rate limit — all transport-level failures that never create a task), the synchronous path (on_task returns a dict and the task walks submitted to accepted to completed with a direct task_result reply) versus the asynchronous path (task_accept then a later pushed task_result, which the client observes by polling), the on_task executor callback contract, and the TaskRegistry state machine with its legal transitions and delegate/server record roles.
